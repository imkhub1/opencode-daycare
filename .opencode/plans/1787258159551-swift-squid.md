# Plan: Schedule Weekly Database Audit

## Objective

Run the OpenDayCare read-only database security audit every Friday at 18:00 in the local timezone of the machine that owns the schedule. Create a real project command for the existing `db-security-auditor` subagent, provide documented examples for every requested scheduling option, and activate only the macOS `launchd` implementation in this repository.

The scheduled audit must not edit the repository or database, apply migrations, use `--auto`, expose secrets, or wait for interactive approvals. Missing LLM or Supabase MCP authentication must produce an explicit blocked/partial result rather than an unsafe fallback.

## Important CLI Correction

The installed OpenCode CLI does not expand `/db-audit` when it is passed as the positional message to `opencode run`; it treats it as plain prompt text. The supported non-interactive invocation of a project command is:

```bash
opencode run --command db-audit --dir "/path/to/06-open-daycare"
```

The launcher and all working examples will use this supported form while documenting that it implements the requested `/db-audit` command semantics.

## Command Contract

`.opencode/commands/db-audit.md` will:

- Invoke `db-security-auditor` as a subtask and define the default parent/child/daycare isolation audit scope.
- Require read-only local and remote metadata inspection, no edits, no migration application, no raw writes, and no interactive approval requests.
- Instruct the auditor to report `BLOQUEADO` or `VERIFICACION_PARCIAL` when authentication or an approved read-only tool is unavailable, without claiming the database is secure.
- Preserve the existing Spanish report contract and secret/PII redaction requirements of `.opencode/agents/db-security-auditor.md`.
- End with a machine-readable `AUTOMATION_RESULT: SUCCESS` only after a completed audit, or `AUTOMATION_RESULT: FAILURE` for blocked/partial/failed execution.

## Cross-Platform Launcher

`scripts/db-audit.mjs` will use only Node built-ins and will:

- Resolve the repository from `import.meta.url`, not the scheduler's current directory, so paths with spaces and scheduled execution are safe.
- Accept `OPENCODE_BIN` as an override and otherwise resolve `opencode` from `PATH`; the macOS plist will set the observed absolute binary `/Users/kevindiaz/.homebrew/bin/opencode`.
- Spawn without a shell using `run --command db-audit --dir <repo>`, with `cwd` set to the repository and an explicit PATH containing OpenCode, Node, `npx`, and system directories.
- Support `--dry-run` to validate the repository, `opencode.json`, binary, command arguments, local timezone, and working directory without running the audit.
- Use an atomic lock outside the OneDrive checkout, skip a second active execution, and remove the lock on normal exit. Document manual stale-lock cleanup.
- Stream output to the scheduler logs, require the success marker, enforce a bounded timeout, and return a nonzero status for CLI failure, missing marker, blocked/partial result, timeout, or missing authentication.
- Set `OPENCODE_DISABLE_AUTOUPDATE=1` and preserve the invoking user's `HOME` so the same user's OpenCode credentials can be used without copying them into a plist or script.

## macOS launchd Implementation

`ops/launchd/com.opendaycare.db-audit.plist` will be a per-user `LaunchAgent`, not a root daemon:

- `Label`: `com.opendaycare.db-audit`.
- `ProgramArguments`: the current Node 24 binary followed by `scripts/db-audit.mjs`.
- `WorkingDirectory`: the full current repository path.
- `StartCalendarInterval`: `Weekday=5`, `Hour=18`, `Minute=0` (Friday at 18:00 local time).
- No `RunAtLoad` and no `KeepAlive`, so loading the agent does not immediately run an audit or create a restart loop.
- `HOME`, `PATH`, `OPENCODE_BIN`, and `OPENCODE_DISABLE_AUTOUPDATE` explicitly set for the scheduled process.
- Standard output and error logs outside OneDrive under `~/Library/Logs/OpenDayCare/`.

The documentation will provide the safe install/update/remove commands using `plutil -lint`, `launchctl bootstrap`, `launchctl bootout`, and `launchctl print`. Activation will be performed only after implementation approval, under the same macOS user that authenticated OpenCode and the Supabase MCP.

## Scheduling Examples Documentation

`docs/db-audit-scheduling.md` will be written in English and will include:

1. **System cron on macOS/Linux**: `0 18 * * 5`, explicit absolute Node/launcher paths, `SHELL`, `PATH`, `HOME`, log redirection, and a note that local cron uses the host timezone. Explain that `launchd` is preferred on macOS.
2. **Windows Task Scheduler GUI**: weekly Friday trigger at 6:00 PM, the Node executable as the program, the launcher as the argument, the repository as `Start in`, same-user credentials, no overlapping instances, and no `SYSTEM` account when user-scoped OpenCode credentials are required.
3. **PowerShell scheduled task**: a script and `Register-ScheduledTask` example using `New-ScheduledTaskAction`, `New-ScheduledTaskTrigger`, `New-ScheduledTaskSettingsSet -MultipleInstances IgnoreNew`, and explicit working directory. Include `-NoProfile -NonInteractive` where PowerShell is the entry point.
4. **macOS launchd**: the repository plist and install, validation, manual kickstart, inspection, and removal commands. Clarify that this is the active implementation.
5. **Supabase Cron / `pg_cron`**: a non-applied illustrative `cron.schedule` plus `net.http_post` request to an authenticated external worker. Explain that Supabase Cron cannot execute a local `opencode` binary, repository checkout, or MCP OAuth session; it can only call SQL or HTTP. Explain that Supabase Cron examples use GMT/UTC, not the local timezone of this Mac, and require a fixed IANA timezone conversion. Require `pg_cron`, `pg_net`, an idempotent authenticated worker, and a managed secret such as Vault; never put a real secret in SQL. No migration will be created or applied.
6. **GitHub Actions**: a non-created workflow example with `schedule`, `workflow_dispatch`, `concurrency`, `permissions: contents: read`, pinned Node/OpenCode versions, checkout, and non-interactive authentication prerequisites. Use the current `timezone` field with an explicit IANA placeholder when the desired local timezone is not UTC. Explain that hosted runners do not have this repository's external `07-DB-Schema` reference, global OpenCode config, MCP OAuth, or provider credentials by default, so the example is not deployable until those dependencies are supplied securely. Do not use pull requests from forks for secret-bearing execution.

Every example will distinguish local-time scheduling from remote UTC scheduling, use 18:00 rather than 06:00, and state that credentials must be provisioned separately. No example will copy `.env`, `SUPABASE_DB_PASSWORD`, service-role keys, Resend keys, invitation encryption keys, or MCP tokens.
