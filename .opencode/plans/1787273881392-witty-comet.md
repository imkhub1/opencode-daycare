# Staff Post Publishing

## Goal

Replace the temporary client-only post composer with a persistent, tenant-safe staff/admin publishing flow. Posts may contain zero to six images. Posts target every active child in one room, remain visible after reload, and are readable by authorized staff/admin users and linked active parents.

## Confirmed Decisions

- Persist posts, recipients, and photo metadata in Supabase.
- Allow active `staff` and `admin` profiles to publish; parents can only read their authorized feed.
- Add a `room_staff` assignment model. Staff publish to assigned rooms; admins can select any room in their daycare.
- Backfill existing staff in `Guarderia Sala Soles` to `Soles`; do not add assignment-management UI in this feature.
- Snapshot all active children in the selected room as `post_children` recipients. Do not trust child IDs from the browser.
- Allow text-only posts even when a child lacks photo consent. Reject any post with photos when any active recipient lacks `photo_consent`.
- Keep the existing seven UI types and persist `ANIMO` as `mood`.
- Unify the sidebar CTA, mobile CTA, composer card, and `/crear-publicacion` around one shared publishing flow.
- Keep reactions, comments, editing, deletion, notifications, and post detail pages out of scope.

## Implementation Plan

1. **Create the approved feature spec.** Add `specs/database/12-staff-post-publishing.md` with the data model, UI behavior, authorization rules, consent policy, upload limits, and acceptance criteria. Cross-reference it from `specs/06-create-post-dialog.md` so the historical client-only scope is not mistaken for the final behavior.

2. **Add the versioned database and Storage migration.** Create a reviewed migration under `supabase/migrations/` that:
   - Adds `post_type` values `meal`, `nap`, `activity`, `achievement`, `mood`, `photo`, and `announcement` plus a non-public draft/published status enum.
   - Creates `room_staff`, `posts`, `post_children`, and `post_photos` with UUID keys, foreign keys, checks, unique constraints, timestamps, and indexes on every RLS/join foreign key.
   - Stores a private Storage path, MIME type, byte size, and position for each photo; never stores expiring signed URLs.
   - Creates a private `post-photos` bucket with the six-photo-compatible MIME and 10 MB limits.
   - Backfills existing active staff in `Guarderia Sala Soles` to the `Soles` room without creating duplicate assignments.
   - Enables RLS, revokes broad table access, and grants only the reads/function execution required by the application.
   - Adds restricted database functions for room resolution, prepare/finalize/abort, and visible-feed reads. Functions derive the caller, daycare, role, room membership, active children, consent, and author from trusted tables.
   - Uses short transactions and a stable lock order when snapshotting room children. No upload is performed while database locks are held.
   - Adds Storage object policies that permit uploads only to an authenticated author's prepared draft and reads only for a published post visible to the current user. Keep the bucket private.

3. **Implement server-side post access and mutations.** Add `app/posts/actions.ts` and server-only query/helpers under `app/posts/` that:
   - Re-authenticate with `utils/supabase/server.ts` and require an active `staff` or `admin` profile on every mutation.
   - Validate type, trimmed description, selected room, photo count, declared MIME, and size on the server using the existing six-file, 10 MB, JPEG/PNG/WebP/GIF limits.
   - Prepare a draft plus the complete active-room recipient snapshot in one database call. Reject photo posts before any upload if consent is incomplete.
   - Return one-time signed upload URLs for prepared photo slots. Upload files directly from the browser with `utils/supabase/client.ts`; do not send up to 60 MB through a Server Action and never expose a service-role key.
   - Finalize only after every expected Storage object exists, re-check the author, draft expiry, room/tenant access, object metadata, and photo consent, then mark the post published and call `revalidatePath("/")`.
   - Allow text-only posts to complete without an upload phase.
   - Abort failed/cancelled drafts with best-effort Storage cleanup and database cleanup; drafts must never be returned by the feed. Keep failure handling safe if Storage cleanup itself fails.

4. **Replace the static feed data path.** Convert `app/page.tsx` into a server entrypoint that loads the current profile, accessible rooms, and visible posts. Pass a serializable DTO to a new client feed/composer component. Remove hardcoded Caro, Mateo, Sofia, Benjamin, dates, and `initialPosts` as the source of truth. Generate short-lived signed read URLs for visible photos on the server.

5. **Extract and reuse the composer UI.** Move the dialog/form interaction from `app/page.tsx` into `components/create-post.tsx` (or an equivalent shared component) while preserving the current accessible modal, focus restoration, Escape/overlay dismissal, drag-and-drop, previews, removal, six-photo cap, and inline validation. Replace hardcoded child chips with the selected room summary; show a room selector only when an admin has multiple accessible rooms. Support the same component in modal mode and full-page mode.

6. **Update feed and navigation components.** Refactor `components/open-daycare.tsx` so `FeedPost` contains only serializable persisted fields and photo URLs, not `File` objects or object URLs. Render real author, room/audience, timestamp, type, description, and photo data. Pass create callbacks only for active staff/admin users so parents cannot see the CTA, while database authorization remains authoritative.

7. **Connect all entry points and route protection.** Make `Compartí un momento...` a button opening the shared modal, add `app/crear-publicacion/page.tsx` for the full-page form, and remove its `crear-publicacion` mapping from `app/[...placeholder]/page.tsx`. Protect the dedicated route server-side and redirect non-staff users to `/`; do not rely on `proxy.ts` for role authorization. Refresh the feed after a successful publish.

8. **Configure image rendering and generated types as needed.** Add the Supabase project hostname to `next.config.ts` if persisted photos continue through `next/image`, and regenerate/update local Supabase TypeScript types if the project introduces a generated database-types file. Keep all new environment usage server-safe and do not add secrets to `NEXT_PUBLIC_*` variables.

9. **Apply and verify the migration through the approved Supabase workflow.** Reconcile migration history first, review grants/RLS/Storage policies and advisor output, then apply the reviewed migration with the project-approved migration workflow. Verify the bucket, catalog objects, backfill, functions, policies, and indexes with read-only queries before relying on the UI.
