# Plan: SPEC 10 - Persisted rooms and child management

## Deliverable

Create `specs/database/10-real-kids-management.md` in English with `Draft` status and date `2026-08-17`. Do not write application code or migrations during the `/spec` workflow.

## Header and dependencies

- Title: `SPEC 10 - Persisted rooms and child management`.
- Objective: replace the static `/kids` experience with tenant-scoped Supabase rooms and persistent staff/admin child lifecycle management.
- Depend on existing SPEC 02 (kids UI/routes), SPEC 04 (add-child dialog), SPEC 07 (daycares), SPEC 08 (users/roles/RLS helpers), and SPEC 09 (authentication/protected routes).
- State that this spec replaces the temporary child behavior from SPEC 04 and removes the static Mateo-only flows from SPEC 02/05 rather than preserving compatibility.

## Scope to record

- Create `public.rooms`, `public.child_status`, and `public.children` in a versioned Supabase migration with grants, indexes, constraints, RLS, and timestamp maintenance where applicable.
- Seed exactly `Soles`, `Lunas`, and `Estrellas` for `Guardería Sala Soles`; seed zero children.
- Keep rooms fixed: no room create, rename, archive, or delete UI.
- Replace all `/kids` mock data with Supabase data and always render the three room sections in that fixed UI order, including per-room empty states.
- Sort children alphabetically within each room and filter the already-loaded collection locally by name.
- Let active staff/admin users create, view, edit, archive, and restore children in their own daycare.
- Show active children by default and archived children at `/kids?view=archived`; archiving requires confirmation.
- Replace Mateo-specific routes with UUID-backed `/kids/[childId]` and `/kids/[childId]/edit` routes. Profiles show only persisted child fields and lifecycle actions.
- Hide the `Niños` navigation item from parents and redirect any parent request under `/kids` to `/`; RLS remains the security boundary.
- Specify loading skeletons, retryable read errors, and inline mutation/form errors that preserve current data and entered values.

## Data model to specify

### `rooms`

- `id uuid primary key default gen_random_uuid()`.
- `daycare_id uuid not null references public.daycares(id)` with restrictive deletion behavior.
- `name text not null`.
- `created_at timestamptz not null default now()`.
- Require a nonblank trimmed name and case-insensitive uniqueness per daycare.
- Keep fixed ordering in the UI, not in a `display_order` column.

### `child_status`

- Enum values: `active`, `archived`.

### `children`

- `id uuid primary key default gen_random_uuid()`.
- `room_id uuid not null references public.rooms(id)` with restrictive deletion behavior.
- `full_name text not null`.
- `birth_date date not null`.
- `enrolled_at date not null`.
- `medical_notes text` nullable.
- `allergy_tags text[] not null default '{}'`.
- `photo_consent boolean not null default true`.
- `status public.child_status not null default 'active'`.
- `created_at` and `updated_at` as non-null `timestamptz` values, with `updated_at` maintained on updates.
- Require a nonblank trimmed name and `birth_date < enrolled_at`; validate `enrolled_at <= today` in the UI/server using the browser-local calendar date for UX and the server UTC date as the final persistence guard.
- Add indexes supporting tenant room reads and room/status child reads; do not add physical-delete capability.

### Allergy normalization

- Parse comma-separated free-form tags, trim, lowercase, and deduplicate.
- Translate the initial known Spanish map: `maní -> peanut`, `lactosa -> lactose`, `gluten -> gluten`, `huevo -> egg`, `leche -> milk`, `soya -> soy`, and `frutos secos -> tree-nuts`.
- Keep normalized unknown values rather than introducing a catalog table.

### RLS and grants

- Reuse the private current-user daycare/role helpers introduced by SPEC 08.
- Restrict room and child reads to active `staff`/`admin` users in the same daycare.
- Restrict child inserts and updates to active `staff`/`admin`; verify both the existing tenant and destination room tenant on room reassignment.
- Give parents no room or child rows and provide no `DELETE` policy/grant.
- Ensure the seed is deterministic for the named daycare and cannot silently attach rooms to another tenant.

## Acceptance criteria to include

- Database catalog checks prove the exact enum, columns, defaults, constraints, indexes, RLS state, policies, and absence of child delete access.
- The target daycare has exactly the three ordered room names and zero children immediately after the migration.
- Staff/admin RLS simulations can read and mutate only their own daycare; parent and cross-daycare simulations return no rows and cannot mutate.
- `/kids` initially shows Soles, Lunas, and Estrellas with empty states and no static child cards.
- A valid child can be created with every persisted field; a reload preserves it and its UUID profile/edit routes work.
- Both client and server reject invalid names/dates, enforce `birth_date < enrolled_at <= today`, and preserve form values after failure.
- Allergy parsing stores the confirmed canonical mappings, normalized unknown values, and no duplicates.
- Consent starts checked and persists both true and false values.
- Active/archived separation, confirmation, `/kids?view=archived`, restore, fixed room ordering, alphabetical child ordering, and local name filtering behave as specified.
- Parents do not see `Niños`, are redirected from all `/kids` routes, and cannot bypass this through Supabase.
- Loading skeletons, read retry, inline errors, invalid/inaccessible UUID handling, mobile/desktop layouts, and browser console behavior are verified.
- `npx tsc --noEmit`, application-scoped lint, and `npm run build` pass, accounting only for the documented pre-existing lint failure in `references/pantallas/support.js`.

## Explicit exclusions and risks

- Exclude room CRUD, parent-child links, invitations, parent counts, daily summaries, posts, room assignment history, physical child deletion, allergy catalogs, photo upload/storage, pagination, server-side search, realtime, and bulk operations.
- Record tenant escape through room reassignment, UI-only authorization, timezone boundaries, case/accent sorting, deterministic seed targeting, and stale Mateo routes as risks with concrete mitigations.
