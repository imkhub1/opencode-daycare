# Plan: Add the `db-migrator` Agent

## Goal

Create a project-scoped OpenCode subagent that reconciles local and remote Supabase migration history, creates a new migration only when an approved database spec requires it, and applies pending migrations through the approved remote Supabase MCP workflow.

Confirmed decisions:

- Require explicit user confirmation immediately before every remote migration application.
- Create migrations only from an unambiguous database spec whose status is `Approved`.
- Target the configured remote Supabase project through MCP. Do not initialize, link, reset, or otherwise prepare a local Supabase environment.

## Scope

Create only:

- `.opencode/agents/db-migrator.md`

Do not modify `opencode.json`, existing agents, skills, specs, migrations already present, application code, dependencies, or migration history.

The file name registers the `db-migrator` agent; no `opencode.json` registration is needed.

## Agent Definition

Use the current OpenCode Markdown-agent schema:

- `description`, `mode: subagent`, the existing project model, and a database-focused color.
- Use `permission:` singular, not the legacy `permissions:` array used by existing files.
- Allow repository reads/searches, deny reads of `.env*` and credential paths, and deny delegation to other subagents.
- Deny edits by default; ask before editing a SQL file under `supabase/migrations/*.sql`. The prompt must additionally require that the target file is new and must never edit, rename, delete, or rewrite an applied migration.
- Deny shell by default, with only narrowly scoped read-only checks such as `git status`, `git diff --check`, and UTC timestamp inspection. If the Supabase CLI is already installed, allow `supabase migration new <name>` only as an explicit approval-gated file-generation command; never allow it to link, reset, push, repair, or otherwise change a database. Never allow destructive Git commands, package changes, or commits.
- Deny all Supabase MCP tools first, then allow only read/validation tools: `supabase_list_migrations`, `supabase_list_tables`, `supabase_list_extensions`, `supabase_get_advisors`, and `supabase_search_docs`.
- Keep `supabase_execute_sql` at `ask` and instruct the agent to use it only for read-only catalog queries; never use it for persistent DDL, DML, grants, seeds, functions, or RLS changes.
- Keep `supabase_apply_migration` at `ask`; it is the only permitted mutating remote operation and requires a second, explicit confirmation in the agent workflow.
- Deny project administration, branches, Edge Functions, Storage, key retrieval, and any other Supabase MCP operation.
- Do not read or expose `.env*`, credentials, service-role keys, passwords, tokens, ciphertexts, or other secrets.

## Agent Workflow

The prompt in `db-migrator.md` should enforce this sequence:

1. Read `AGENTS.md`, the Supabase skill, the Postgres best-practices skill, the relevant approved spec, related migrations, and the `db-schema` reference. Treat approved specs and current migration history as authoritative over the conceptual reference.
2. Identify the requested database spec explicitly. For a new schema change, stop if the spec is missing, not exactly `Approved`, ambiguous, out of scope, or conflicts with existing code, specs, or migrations. Do not infer schema requirements silently from application code.
3. Inspect the working tree and preserve unrelated user changes. Inventory local migration files, validate their 14-digit versions and ordering, detect duplicate/invalid names, and identify already-applied files that must remain immutable.
4. Query remote migration history for the configured project and reconcile local and remote identities by version/name. Stop on remote-only migrations, missing predecessors, version/name conflicts, schema drift, or a migration that appears applied but has missing expected objects. Do not skip, reorder, renumber, consolidate, or repair history.
5. If a new migration is genuinely required, create one versioned file using the approved project convention and a current UTC-generated version. Prefer `supabase migration new <name>` when available solely to create the file; if that cannot be done safely without inventing a version, stop and report the blocker. Edit only that new file and keep its SQL limited to the approved spec.
6. Review the candidate diff, run `git diff --check`, review relevant Supabase documentation/changelog, and collect the pre-application advisor state. Show the exact migration name, project reference `buhfslxahextimvdfveh`, SQL scope, affected objects, and risks.
7. Ask for an unambiguous confirmation immediately before applying. Require confirmation for each migration separately; prior general permission is not sufficient. Do not invoke `supabase_apply_migration` if the user declines or the project reference cannot be verified.
8. Apply one migration at a time through `supabase_apply_migration` using the exact migration name and SQL query. Never use `execute_sql` for persistent changes, and never use `db push`, `migration repair`, or compensating SQL. Read-only `execute_sql` catalog queries remain limited to verification.
9. After each successful application, verify remote history and read-only catalogs for tables/columns, enums, constraints, indexes, functions, triggers, grants, RLS, policies, and expected non-sensitive seeds. Re-run advisors and report any new findings. Mark the outcome as partial when verification is unavailable or ambiguous.
10. On timeout or failure, first determine whether the migration was applied by querying history/catalogs, then stop. Never retry blindly, rollback automatically, edit the failed migration, or claim success with unknown state. Do not update spec status or create a commit.

## Response Contract

Require a concise Spanish report with these fields:

- `Estado`: `BLOQUEADO`, `SIN CAMBIOS`, `ESPERANDO_CONFIRMACION`, `APLICADO`, or `APLICADO_CON_VERIFICACIÓN_PARCIAL`.
- `Spec`: path, status, scope, and dependencies.
- `Preflight`: local files, remote history, advisors, and discrepancies.
- `Migración`: existing or newly created path, version, name, and affected objects.
- `Aplicación`: confirmation state and MCP result, without secrets.
- `Verificación`: history, catalogs, RLS, policies, grants, and advisor results.
- `Archivos modificados`: only a newly created migration, if applicable.
- `Bloqueadores`: concrete reason and next required user decision.

Repository instructions and agent prompts remain in English; the agent communicates results to the user in Spanish.
